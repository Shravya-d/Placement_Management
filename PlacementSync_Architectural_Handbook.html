1. High-Level Architecture (3-Tier & Decoupling)

PlacementSync is engineered on a decoupled client-server-database (3-Tier) architecture. This structural separation guarantees that the presentation layer (frontend), application logic layer (backend), and data storage layer (database) remain distinct, communicating only through formal interfaces (RESTful APIs and Mongoose ODM drivers).

Architectural Tiers

1. Presentation Tier (Frontend Client)

Developed as a Single Page Application (SPA) using React 19 and Vite. It executes entirely within the user's web browser, managing view logic, UI routing (client-side), local session stores, and custom micro-animations. It never talks directly to the database; it accesses data by sending asynchronous HTTP requests containing JWT credentials to the API Gateway.

2. Logic Tier (Backend REST Server)

An Express application running on the Node.js runtime. It acts as the single point of entry for all API requests. The logic tier is fully stateless—sessions are validated via JWT tokens sent in cookies or authorization headers. It contains controllers that interpret client requests, services that enforce business rules and run algorithmic logic, and middleware functions that guard against unauthorized access.

3. Data Tier (Database Engine)

A MongoDB document-based database. Document-oriented storage matches the application's object structures, removing the need for complex object-relational mapping (ORM) translations. Relationships are represented either by embedding arrays of structures directly within documents (maximizing read speed) or by storing ObjectIds as pointers to other documents (preventing data duplication).

Architect's Note: Benefits of Decoupled Architecture

By keeping these layers separate, we can update or scale any tier independently. For example, the React frontend can be completely rebuilt or hosted on a CDN (Content Delivery Network) like Vercel without requiring changes to the Node.js API logic or database structures.

2. Backend Stack & Core Libraries

The backend handles API requests, schedules notifications, runs matching algorithms, and coordinates data migrations. Below is a detailed breakdown of each backend library and dependency used in the project:

Core Frameworks & Runtimes

Node.js Runtime

An asynchronous, event-driven JavaScript runtime built on Chrome's V8 engine. It uses a single-threaded event loop and non-blocking I/O to handle thousands of concurrent requests efficiently.

Express.js (v4.18.2) Framework

A minimal, unopinionated routing and middleware web framework for Node.js. It manages routing pipelines, parses incoming request bodies (via express.json()), and processes requests through a chain of middleware functions.

Database & Modeling

Mongoose (v7.5.0) ODM Library

A schema-based Object Data Modeling (ODM) library for MongoDB and Node.js. It manages MongoDB connections, enforces schemas at the application level, handles data type conversions, provides built-in validation, and offers a middleware API (hooks like pre('save')) for hashing passwords.

Security & Validation Libraries

jsonwebtoken (v9.0.2) Authentication

Enables stateless session management by signing and verifying cryptographically secure JSON Web Tokens (JWT). Once credentials match, the server signs a token using the HMAC-SHA256 algorithm and the server's private secret. The token is verified on subsequent requests to load user data without database lookups.

bcryptjs (v2.4.3) Cryptography

A pure-JavaScript implementation of the bcrypt password hashing function. It secures user passwords before storing them in the database. It adds a random "salt" value and hashes the password multiple times (12 rounds) to protect against brute-force and rainbow table attacks.

Helper & Utility Packages

cookie-parser (v1.4.7) HTTP Utility

Parses the Cookie header in incoming HTTP requests and populates req.cookies. This allows the backend to read HTTP-only session cookies containing the JWT token, which protects against Cross-Site Scripting (XSS) attacks.

cors (v2.8.5) Security Middleware

An Express middleware that configures Cross-Origin Resource Sharing (CORS) headers. It allows the frontend application (running on port 5173) to securely communicate with the backend API (running on port 5000) using credentials (cookies).

dotenv (v16.6.1) Configuration

Loads environment variables from a local .env file into Node's process.env object. This separates application configurations (like API keys, database connection strings, and JWT secrets) from the code, preventing security leaks.

morgan (v1.10.1) Logging

An HTTP request logger middleware for Node.js. It formats and prints details of incoming requests (method, status code, response times) to the terminal, which simplifies debugging in development environments.

3. Frontend Stack & UI Libraries

The frontend application is built to deliver a fast, responsive user experience. Below is an explanation of the core technologies, frameworks, and libraries used to build the client-side app:

Core Client Frameworks

React 19 & React DOM (v19.2.4) UI Library

A declarative, component-based JavaScript library for building user interfaces. React 19 manages a Virtual DOM to optimize updates and minimize direct browser rendering calls. It uses a component hierarchy to make views modular and reusable.

Vite (v8.0.1) Build Tool

A modern frontend build tool that leverages native ES modules in the browser. It offers extremely fast Hot Module Replacement (HMR) during development and uses Rollup to optimize assets for production.

React Router DOM (v7.13.2) Client Routing

Manages client-side navigation and routing. It maps browser URLs to specific React views (like dashboards, login pages, and profiles) and intercept browser transitions to prevent full page reloads, preserving state.

State Management & Syncing

Zustand (v5.0.12) Client State Store

A lightweight state management library. It uses a simple publish-subscribe model to manage global states (like user credentials and roles) without the boilerplate of Redux. It includes a persistence middleware (persist) to automatically save auth data to localStorage.

React Query / @tanstack/react-query (v5.95.2) Server State Manager

Manages asynchronous data fetching, caching, synchronization, and state updates from the server. It tracks loading, success, and error states, caches API responses, and handles background revalidations. This ensures the UI stays updated without duplicate network requests.

Animations & Data Visualization

GSAP / GreenSock & @gsap/react (v3.14.2) Animations

A high-performance HTML5 animation library. It handles complex CSS transitions, layout changes, and scroll-triggered animations. It uses high-performance rendering engines to keep animations smooth and responsive.

Recharts (v3.8.1) Data Visualizations

A chart library built with React and SVG elements. It parses backend statistics and renders interactive charts (line graphs, bar charts, and pie charts) on the analytics dashboard.

Form Handling & Styling

React Hook Form & Zod Resolver Forms & Type Safety

Performs client-side form validation. react-hook-form minimizes re-renders by tracking inputs directly, and zod parses form data against a schema to check inputs before they are sent to the backend.

Tailwind CSS & Autoprefixer Styling Framework

A utility-first CSS framework. It enables rapid UI development directly in React components using responsive styles. It is bundled with Autoprefixer to ensure CSS compatibility across different web browsers.

4. Database Schema Design & Relationships

The database is built on MongoDB, a document-based NoSQL database. Mongoose enforces types and handles data validation. Below is a detailed breakdown of the collection schemas and how relationships are modeled:

Collection Design & Schemas

1. Student Collection (students)

Stores active, unplaced candidates. It contains the candidate's credentials, branch, CGPA, and an array of skills.

Relational Strategies & Indexes

  • Embedded Arrays (One-to-Many): Applications are embedded inside the Student document, and recruiter drives are embedded inside the PlacementDept document. This allows the system to retrieve related data in a single database read, avoiding costly JOIN operations.
  • Referential Keys (One-to-One / Many-to-Many): Points are stored as mongoose.Schema.Types.ObjectId references (like the link between Interview and Student) where embedding would cause document size limits (16MB) to be exceeded or result in stale data.
  • Performance Indexes: To keep query response times fast, we define database indexes on frequently queried fields:
    • studentSchema.index({ placementStatus: 1 }): Optimizes dashboard queries when filtering candidates.
    • studentSchema.index({ branch: 1, cgpa: -1 }): Speeds up company eligibility checks.
    • studentSchema.index({ skills: 1 }): Accelerates skill similarity match calculations.

5. Core Feature: Interview Scheduling Subsystem

Problem Solved: Organizing interviews manually is error-prone, leading to double-bookings, lost link details, and manual update delays.

Solution: An integrated Interview Scheduling Subsystem that manages bookings, updates statuses across documents, and links directly to student dashboards.

Technical Mechanics: When an admin assigns an interview slot, the server creates a new document in the Interview collection. In a transaction-like sequence, it also updates the status to INTERVIEW_SCHEDULED in both the Student document and the company's applicant subdocument.

Key Code Block Trace (Interview Allocation)

Implemented in backend/src/controllers/interviewController.js:

exports.assignInterview = catchAsync(async (req, res, next) => {
    const { studentId, companyId, date, time, mode, meetingLink, location } = req.body;

    // 1. Verify student has actually applied
    const student = await Student.findById(studentId);
    if (!student) return next(new AppError('Student not found', 404));

    const application = student.applications.find(app => app.companyId.toString() === companyId);
    if (!application) return next(new AppError('Student has not applied to this company', 400));

    // 2. Prevent overlapping interviews
    const existing = await Interview.findOne({ studentId, companyId, status: 'scheduled' });
    if (existing) return next(new AppError('An active interview is already scheduled.', 400));

    // 3. Create Interview Document
    const newInterview = await Interview.create({
        studentId, companyId, date, time, mode, meetingLink, location, status: 'scheduled'
    });

    // 4. Update status in Student collection
    await Student.updateOne(
        { _id: studentId, 'applications.companyId': companyId },
        { $set: { 'applications.$.status': 'INTERVIEW_SCHEDULED' } }
    );

    // 5. Update status in PlacementDept embedded company applicants array
    await PlacementDept.updateOne(
        { 'companies._id': companyId, 'companies.applicants.studentId': studentId },
        { $set: { 'companies.$[comp].applicants.$[app].status': 'INTERVIEW_SCHEDULED' } },
        { arrayFilters: [{ 'comp._id': companyId }, { 'app.studentId': studentId }] }
    );

    res.status(201).json({ status: 'success', data: { interview: newInterview } });
});

Frontend Integration

The admin accesses the Selection Center screen. Under "Applied" applicants, clicking **Assign Interview** triggers a modal to input the date, time, mode (online/offline), and meeting link/location. This fires the useAssignInterview mutation hook, which calls the backend endpoint. On the candidate side, StudentDashboard.jsx fetches the updated interview array and displays dates, times, and meeting links with a virtual "Join Meeting" button.

6. Complete End-to-End System Workflow Trace

Below is the complete flow of the PlacementSync system, tracing data movements and actions from project setup to final selection and alumni reviews:

Step-by-Step System Flow

Step 1: Admin Adds a Company Drive

The placement admin fills out a company form (defining name, role, required skills, minimum CGPA, backlog gate, allowed branches, and deadline date). This POST request goes to /api/placement/companies, calling placementDeptController.addCompany.

Step 2: Broker Auto-Matches Candidates

Inside addCompany, the server calls matchingService.matchStudentsToCompany(newCompany). The service scans the Student collection for unplaced students. If they pass the branch, backlog, and CGPA requirements, the company's ObjectId is added to their eligibleCompanies array, and they receive an automated email alert via emailService.js.

Step 3: Student Learns Missing Skills

The student opens their dashboard. The UI renders the matched companies. The student clicks **View Eligibility** to open the eligibility modal. This calls studentController.getCompanyEligibility $\rightarrow$ eligibilityService.evaluateStudentEligibility. If the student is missing skills, courseService.js fetches tutorial courses from the YouTube API (or cache) and displays them as clickable learning cards on the student's dashboard.

Step 4: Student Submits Application

The student clicks **Apply** on their dashboard. This triggers a POST to /api/student/companies/:companyId/apply $\rightarrow$ studentController.applyToCompany. The backend validates the student's eligibility, pushes the application record into the student's applications array, and adds the applicant details to the company's embedded applicants array.

Step 5: Admin Evaluates Candidates (Anonymous Mode & NLP Matching)

The admin opens the Selection Center. This calls placementDeptController.getCompanyApplicants. The server calculates the semantic similarity score between the student's skills and the job description using the Jaro-Winkler algorithm. If anonymousMode is enabled for the company, the candidate's personal details (name, email, phone, USN) are obfuscated before the list is sent to the client.

Step 6: Admin Schedules Interview

The admin clicks **Assign Interview** for a candidate. This calls interviewController.assignInterview, creating a document in the Interview collection and updating the status to INTERVIEW_SCHEDULED across the system.

Step 7: Admin Marks Interview as Completed

Once the interview is finished, the admin clicks **Mark Completed**. This updates the interview status in the database to completed. The student's application status updates to COMPLETED, which flags them in the admin dashboard for final placement decision.

Step 8: Admin Places or Rejects Candidate

The admin has two options for processed candidates:

  • Place: Clicking **Place** triggers placementDeptController.selectStudents. This marks the applicant as placed, creates a new record in the Alumni collection, copies their profile and credentials, deletes their active record from the Student collection, and sends a congratulations email.
  • Reject: Clicking **Reject** triggers placementDeptController.rejectStudents. This updates the applicant's status to REJECTED in the drive and the student document, and sends a rejection email.

Step 9: Background Cron Notification Alerts

Every 5 minutes, cronService.js checks for company drives with application deadlines expiring in less than 1 hour. It finds eligible students who haven't applied yet and dispatches urgent warning emails.

Step 10: Alumni Network & Feedback Loop

Placed students can log into their dashboard as Alumni. They can use the Alumni Portal to search for classmates and view colleagues' contact details. They can also submit rating reviews and interview feedback for the company they joined, which is nested under the company's feedbacks array for current students to read.

7. Algorithmic Implementations

PlacementSync uses custom backend algorithms to automate skill matching and calculate profile compatibility scores:

A. Jaro-Winkler Semantic Similarity Matcher

Simple string comparisons fail when candidates use slight variations of terms (e.g., "NodeJS" and "Node"). The Jaro-Winkler algorithm measures character substitutions and transpositions to determine how closely two terms align.

It is calculated as: $$d_j = \frac{1}{3} \left( \frac{m}{|s_1|} + \frac{m}{|s_2|} + \frac{m-t}{m} \right)$$ Where $m$ is the number of matching characters, $|s_i|$ is the string lengths, and $t$ is the number of transpositions. Jaro-Winkler scales this score based on the length of matching prefixes: $$d_w = d_j + \ell p (1 - d_j)$$ Where $\ell$ is the prefix overlap length and $p$ is a constant scaling factor (typically 0.1).

Our implementation in similarityService.js loops through each skill in the job description, finds the highest Jaro-Winkler similarity score against the candidate's skills, and aggregates these values to compute a combined matching percentage.

B. Profile Eligibility Weighting Formula

The compatibility engine splits score calculations into two categories:

  • Hard Gate Filters: If the company limits applications by branch (e.g., computer science only) or backlog constraints (no active backlogs allowed), and the candidate fails to meet these criteria, their eligibility is set to false immediately.
  • Weighted Scores: If the hard gates pass, the system calculates a compatibility percentage:
    • CGPA (60% weight): If the candidate's CGPA is greater than or equal to the requirement, they receive the full 60 points. If it is slightly lower, they receive a proportional score: $$\text{Score}_{\text{CGPA}} = \left( \frac{\text{Student CGPA}}{\text{Required CGPA}} \right) \times 60$$
    • Skills Overlap (40% weight): Calculated as the percentage of required skills matched: $$\text{Score}_{\text{Skills}} = \left( \frac{\text{Matched Skills Count}}{\text{Required Skills Count}} \right) \times 40$$
    The final compatibility score is calculated as: $$\text{Score}_{\text{Total}} = \text{Score}_{\text{CGPA}} + \text{Score}_{\text{Skills}}$$

8. Security Implementations & Route Protection

Security is built into the backend to protect sensitive student records and administrator controls.

Authentication Architecture

  • Stateless Sessions: Authentication uses stateless JSON Web Tokens (JWT) rather than server-side session stores, allowing the backend to remain stateless and scale efficiently.
  • Password Cryptography: Passwords are hashed using bcryptjs with a work factor cost of 12. Passwords are never stored in plain text, protecting credentials even in the event of a database compromise. The field is configured with select: false to prevent credentials from being exposed in standard query results.
  • HTTP-only Cookies: The JWT is returned in a cookie configured with the httpOnly flag. This prevents client-side scripts (like JavaScript) from reading the token, protecting sessions from Cross-Site Scripting (XSS) attacks.

Route Authorization Pipeline

Incoming requests are checked by middleware layers before reaching controller functions: 

[Incoming Request]
        │
        ▼
[auth.protect Middleware] 
  - Extracts JWT token from Cookie or Bearer header.
  - Verifies token signature using JWT_SECRET.
  - Decodes user ID and checks DB to verify the user exists.
  - Attaches user record to req.user.
        │
        ▼
[role.restrictTo('admin') Middleware]
  - Compares the role field in req.user.role with allowed roles.
  - Throws HTTP 403 error if roles do not match.
        │
        ▼
[Route Controller Handler]
  - Executes request logic.

9. Architectural Design Patterns & Tradeoffs

PlacementSync uses established software design patterns to structure its codebase. Below is an explanation of the design patterns used, and the tradeoffs associated with our architectural decisions:

Design Patterns

  • Layered MVC (Model-View-Controller) Architecture: Divides logic into distinct layers. Routers define API paths, controllers process request arguments and format responses, and services manage domain operations and database models.
  • Adapter Pattern: Implemented in the course recommendations integration. The service translates dynamic YouTube video responses or scraper outputs into a consistent, unified JSON format, protecting client views from changes in external API structures.
  • Publish-Subscribe Pattern: Zustand manages client state using state subscriptions. React components subscribe to specific fields in the store and re-render only when those specific fields change, improving rendering performance.

System Tradeoffs

Tradeoff: Nested Recruiter Drives in PlacementDept

Company drives and job listings are stored as embedded documents within the PlacementDept collection rather than using a separate, referenced collection.

  • Tradeoff Analysis: Embedded models allow the system to load admin dashboards and candidate lists in a single database read, avoiding JOIN operations. However, MongoDB enforces a 16MB limit on individual documents. If the college lists thousands of companies over time, the document could exceed the limit, causing database errors.
  • Mitigation Strategy: As the system grows, refactor the schema to store companies in a standalone collection, referencing the department ID via ObjectIds.

Viva & Technical Interview Q&A

Q1: Why does the system clone placed students to the Alumni collection and delete their record from the Student collection?

Answer: This keeps the active Student collection small, which improves database query and indexing performance. It also separates active candidates from placed alumni, simplifying dashboard queries.

Q2: What is Jaro-Winkler Distance, and how does the system use it for skill matching?

Answer: Jaro-Winkler is a string similarity metric that measures the edit distance between two strings, giving higher scores to prefix alignments. The system uses the natural library to compare student skills with job descriptions, ensuring variations like "React" and "ReactJS" are matched successfully.

Q3: Explain the security benefits of using HTTP-only cookies to store session JWTs.

Answer: HTTP-only cookies cannot be read by client-side JavaScript. This protects the token from being accessed during Cross-Site Scripting (XSS) attacks, securing the user session.

Q4: How does the upskilling recommender handle rate-limiting or network issues during course lookups?

Answer: The service implements a caching and fallback pipeline. It first checks the local MongoDB cache. On a cache miss, it queries the YouTube API. If the key is missing or rate-limited, it falls back to screen scraping via youtube-search-api, and defaults to a general Google search if both fail.
